Member Risk AI-DLC Blueprint

How every change moves from idea to production: specs approved and locked, code built by agents with skills, reviewed by an AI reviewer, approved by code owners, and rebuilt automatically, in a repo where each lifecycle stage is an independent, config-driven module.

      4. Every stage is the same self-contained module

      Stages never import each other. They talk only through versioned Delta tables whose schema is declared in each stage's contract.yaml. That's what lets one stage change, rerun or be replaced without touching the others.

      config/stage.yaml

      Inputs, outputs, parameters, feature flags. Most changes are edits here, with no code.

      config/<registry>.yaml

      Plug-in lists: sources, features, selection methods, models, monitors. Add an entry to add a capability.

      contract.yaml

      Input and output table schemas and keys. The pipeline checks contracts before a stage runs.

      src/

      Stage logic, plus plugins/ for registry entries. Uses only common/ helpers, never another stage.

      tests/

      Unit, leakage and contract tests. The review agent and CI run them on every PR.

      skills/ + AGENTS.md

      Local skills and rules the coding agent loads when working in this stage, on top of the global ones.

      job.yml

      This stage's Databricks job (bundle resource). Runs alone or as a task in the full pipeline.

      CODEOWNERS entry

      One owner group per stage. Only they can approve changes to it.

      README.md

      What the stage does, its contract and how to extend it. Linked from its spec.

      5. Rules that keep it automated and safe

      1. One change, one branch, one spec folder. feature/NNN-name with specs/NNN-name/ (spec, plan, tasks).
      2. No code before an approved spec. /speckit.analyze must be clean; the tech lead approves; the approval (name, time) is written to gates/ and the spec is locked by CODEOWNERS.
      3. Changing a locked spec reopens approval. Any edit to an approved spec needs the spec owner again and starts a new pipeline run on the branch.
      4. Every changed file is named by a task with the FR IDs it implements; the review agent blocks untraced code and assumptions.
      5. Only code owners approve their stage. Branch protection: PR required, owner approval, AI review and CI must pass.
      6. Reruns start at the earliest changed stage and flow downstream through the contracts. Nothing upstream reruns.
      7. The evaluation in 05_model_test is locked. Models compete on it; only the model owner can change it.
      8. Agents propose, people decide. Agents never merge, promote or deploy to production.
